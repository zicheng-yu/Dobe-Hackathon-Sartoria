- 明确写出的 `conflicts: []` 要求预览没有冲突。写出冲突字段时按集合精确比较。`holdout2.ts` 里省略的冲突字段未标注，该项单列为不评分。`fixtures.ts` 和 `holdout.ts` 继续沿用冻结时的约定，省略表示预期没有冲突。无论冲突项是否有标注，提议变更字段、确认后的全量硬条件、未改条件及其来源、预览隔离、归档状态、重开及导出均按原口径检查。
- `unknowns` 是需要保持未决或未选定的字段。明确排除值与尚未选定具体值可以同时存在。`followUpFields` 挑出会阻塞决策的字段，最多两问。未指定的字段可出现在设计建议和交接记录中，客户硬要求应有可回查的原话。
- `catalog` 给出可行、无合格方案或冲突阻断的地面判定，以及静态目录证据。存在合格方案时，`requiredIds` 可由任一合格组合共同满足。明确违约只能拒绝，关键证据缺失可待核，历史案例只能作参考。

## 复跑

第二批初测发现漏判后，本轮另设最后一批 24 条留出简报。独立标注者只使用静态目录、数据合同与评分说明。该批每个改稿预览显式标注冲突字段（含空集合），按同一放行门槛检查，保存候选第一次运行结果。诊断后的任何重跑都记为回归，本轮到此停止追加盲测样本。

11 月 24 日的后续自由文本复验使用第四批新样本，产品固定为 `2683959`。三名独立作者依据共享类型和静态目录标注 24 条委托、36 轮消息。先冻结标签，再将原消息用于已有的放行评分。另外把每条首轮消息的标点改成换行或空格，记录硬约束、候选和违约变化。这 48 次排版扰动仅用于敏感性分析。

第五批复验固定 [PR #5](https://github.com/zicheng-yu/Dobe-Hackathon-Sartoria/pull/5) 的产品提交 `51a8295`。独立作者只参考字段合同和静态目录，重新编写 24 条委托、36 轮消息，在运行产品前冻结预期。沿用第四批的门槛及首轮排版扰动。复核这一成绩需要检出同时包含该产品和第五批评测的版本。

`npm run test:release` 逐批运行五组冻结验收，每组 24 条。命令核对候选版本并生成报告，任一放行断言失败即返回非零状态。将 `SARTORIA_RELEASE_SUITE` 设为 `1` 至 `5` 可单独复跑。设置 `SARTORIA_RELEASE_SHA` 可核验指定提交，当前源码、评分代码、样本和运行配置须与该提交一致。报告写入 `node_modules/.cache/sartoria-baseline/`，首批为 `release-<SHA>.json`，其余为 `release-<批号>-<SHA>.json`。

`npm test` 包含原始 24 条简报、32 条色彩对照、11 条跨字段控制和七份订阅子代理的首次 Astra 回答。色彩对照按原话核验当前用色、排除、偏好与待核状态。目录外的明确必选和排除须带原话并阻断推荐，有条件的候选和普通偏好须保留原话并允许继续选配。Astra 回放在本地运行 Worker 和前端客户端，上游传输始终从冻结文件读取，项目 API 调用为零。单跑色彩和 Astra 用例可使用 `npm test -- evaluation/colorScope.test.ts evaluation/astraReplay.test.ts`。

在仓库根目录使用 Node.js 24，安装锁定依赖后运行 `npm exec -- vitest run evaluation/blind.test.ts`。记录评测时新版本 SHA 和冻结样本哈希。断开模型路径并清空项目历史，按相同原文和顺序分别运行纯本地基线与新版本。

基线源码固定到 `4e0d95921683fd04cf7834b754b02687d73d56a6`。从该提交用 `git archive` 读取到一次性目录 `node_modules/.cache/sartoria-baseline`，使用旧版目录与旧版 `deconstructLocally → recommendInitialConfig → evaluateFeasibility`。两版使用相同的空白表单和固定必填默认值，保留原始简报，禁用预设。默认业务、季节和场景不得作为抽取结果，也不从预期标签补填。旧版只映射其明确标为客户要求且可无歧义归一的字段。无法归一的描述保留在失败证据中。旧版没有原生改稿的步骤记为不支持，可另列拼接原话重跑的结果。

## 判分

| 项目 | 口径 |
| --- | --- |
| 硬约束 | 首轮按 24 条简报汇总。按每条去重后的 `(field, op, value)` 精确比较，报告 TP、FP、FN 与微平均精确率、召回率。单列 `neq` 的同口径指标。另查引文是否确切存在于来源轮次且支持对应约束。 |
| 组合可信度 | 记录库外推荐 ID、标成可行的已知违约、无证据的洗护/合规断言。以各版所用目录及已标注阻断项审计实际推荐，缺失证据不得算通过。检查无匹配说明与拒绝理由。历史案例不能填补成衣事实。 |
| 补录和纠正 | 每个已完成样本按字段记数。漏填一项硬要求算一次补录。错误、被覆盖、误升为硬要求或无法归一的明确承诺算一次纠正。单字段同时出现错误与缺失时合并为一次纠正。另记不安全候选需改选的次数。报告样本分母。 |
| 改稿 | 逐轮对比预览涉及字段与确认后的字段集，检查未改硬约束及其来源是否保留。冲突在确认前不得改写旧版；取消保留草稿；挂起继续展示待定项。按指定操作跑完整的预览、确认、重开及导出，检查旧版快照和选中版本的导出内容，逐条报告通过的链路。 |

特指场地按静态目录 ID 审计，场景类别按分类审计。首轮放行仍使用精确三元组。附加指标 `decisionEquivalentHard` 仅在运算符一致、两种表达允许的非空目录场地集合完全一致时合并计分，缺少类别证据的场地不能作为该类别排除项的通过依据。改稿对照金标时可使用同一集合等价规则，比较改稿前后原始硬条件及其来源时仍要求原值和原话逐项保留。

放行按 PRD 报分母：硬约束精确率与召回率各 ≥90%，24 条中三类组合可信度错误均为 0，6 条改稿全部保留未改硬约束，至少 5 条完成整条回放。记录实际成功数和代表性失败。首轮、改稿、独立录屏演示分开报告。
## 放行线未满足时的录屏流程

1. 在需求工作台新建秋季会务简报。现场核对数量、室内场合、藏青、耐皱、机洗和排除的传统制服风格，展示原话出处与人工确认入口。
2. 比较模拟目录中的两套合格组合。点击洗护证据和拒绝理由，说明真丝候选的洗护缺证。让业务专员选择通过硬筛的方案并保存 V1。
3. 粘贴客户的亮度和真丝反馈，展示冲突及待核项后由业务专员选择处理方式。强调目录只覆盖已验证的组合。若无合格组合，保存待核版供人工接手。
4. 打开项目档案，重开已保存的版本并下载对应 JSON 或 Markdown。现场引用该版本的原话、人工选择、需要补证的字段与负责人。对照放行情况见 [RESULTS.md](RESULTS.md)。
